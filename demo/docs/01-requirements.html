内容运营后台 CLI 化：需求与接口分析

0. 分析范围与依据

本文件用于理解业务、核对接口、识别约束和比较第一阶段范围；不确定技术框架，不定义正式技术设计，不实现 CLI，也不执行审核或修改附件数据。

已完整读取并解析以下材料：

材料 用途与核对结果
题目：内容运营后台 CLI 化.md 业务背景、三项任务、1 名后端与 2 周资源约束
附件 README 接口与数据的使用说明；明确允许本地假数据演示，不要求真实联网
content-ops-admin-openapi.json OpenAPI 3.0.1，接口版本 1.2.0；实际为 21 个路径、23 个操作
mock_data.json 全量遍历七类业务数据，检查数量、字段类型、枚举、状态、引用、时间和跨对象一致性
内容运营后台接口数据.zip 核对其中三个文件与现有解压目录的文件，逐文件 SHA-256 一致

证据口径：

  • 题目要求：来自原题的明确要求。
  • 现有行为：来自 OpenAPI 的描述、请求/响应 schema；示例单独注明，不把示例值当作固定规则。
  • 数据事实：来自本次对完整 mock_data.json 的计算；不能直接外推为生产系统规律。
  • 分析/建议：我们对 CLI 使用方式和风险的判断，不表示现有系统已经提供这些能力。
  • 待确认：材料没有给出，不能默认支持，也不能据此断言生产系统绝对没有。

下文接口均以 OpenAPI 的 paths[路径][方法] 为依据，字段以 components.schemas 为依据。未使用外部资料。服务地址 https://api.example.invalid 是不可访问的占位地址；本次没有联网调用。

1. 主要结论

  1. CLI 的核心业务闭环是“找到待审核内容 → 查看详情与必要上下文 → 作出审核决定 → 更新标签 → 核对结果”，不需要把 23 个操作全部包装一遍。
  2. 三项任务直接依赖的接口集中在内容查询、详情、审核记录、审核提交、标签库读取、内容标签更新，共 6 个操作。其中审核记录和标签库属于辅助判断/校验能力。
  3. 100 条处理的主要难点是结果可判定、重复执行和恢复，不只是拆成 5 个审核请求：审核接口只返回成功/失败计数，重复提交会追加审核记录，标签又只能逐条全量覆盖。
  4. 当前合同没有声明审核与标签更新的联合事务、请求幂等键、版本条件或可验证的调用者身份。CLI 可以降低误操作和保留执行证据，但不能自行承诺服务端“恰好执行一次”或并发写入安全。
  5. 样例包含 300 条内容，其中待审核 132 条。数量足够支持任务二及 100 条演示，但存在空正文、分发约束冲突、日志时间和状态不一致等问题，必须区分正常演示数据与异常验证数据。
  6. 原题要求的是第一阶段产品方案、评审交付物、操作说明和 Agent/100 条场景变化说明，并未明确要求覆盖全部后台、实现自动审核模型或提交可运行 CLI。本轮只交付分析。

2. 业务需求理解

2.1 现有后台的业务场景

场景 运营目的 现有接口提供的动作 需要区分的语义
内容定位与审核 从待审核池中识别内容、查看正文和历史、通过或驳回 列表、详情、审核记录、批量审核 列表不含正文；审核状态不是可见性或质量状态
内容标签维护 整理题材、风格、运营标签，辅助检索与运营 查询/创建标签、替换内容标签 内容标签更新是全量覆盖；不会自动校验标签库
分发与曝光运营 配置栏目、渠道及推荐位 栏目查询、内容分发、推荐位查询/占用 栏目限制可用渠道；推荐位有时间冲突和线上曝光影响
内容处置 降低分发量、下架、恢复 质量状态、可见性调整 限流不等于下架；下架即时生效；质量调整不通知创作者
创作者管理 了解作者情况，维护快速审核资格 创作者列表/详情、白名单设置 白名单豁免部分自动风控，影响大于普通资料维护
举报与沟通 核实用户举报、回销、向创作者通知 举报列表/回销、站内通知 回销不处置内容；发通知是独立、即时送达的动作
追踪与复盘 查看操作轨迹、导出、统计工作量 操作日志、异步 CSV 导出、审核日报 API 操作人统一为 op_api；日报 T+1，不能用于当天实时核验

内容有三个不同维度：

  • review_status：pending / approved / rejected，审核判断。
  • quality_status：normal / limited，质量和分发限制。
  • visibility：online / taken_down，可见性。

分析：应分别展示与核对这三个维度。附件没有给出完整状态迁移规则，不能推导“通过就自动上架”“驳回就自动下架”“通过就解除限流”。样例确实存在 rejected + online 和 pending + limited，也不能仅凭这些组合判定数据错误。

2.2 CLI 化要解决的问题

题目明确提出的动机是：网页操作之外，运营人员、脚本和 Agent 需要复用同一套后台能力。

从后端角度，这意味着需要把面向网页的接口转为可重复、可组合、可观察的操作入口：明确选择对象，暴露真实写入语义，区分整体成功与部分成功，让调用方知道失败后能否继续。减少网页点击和人工搬运只是价值之一；更关键的是同一业务动作在三种调用方式下具有一致含义。

以下为产品需求分析，不是现有接口已实现的功能：

使用者 输入与交互需求 输出与失败处理需求 特有关注点
运营人员 易发现命令，按筛选条件找到对象，阅读正文；看清标签变化和操作影响 可读表格、明确的逐步结果；出错后知道哪个步骤已完成 中文、长标题、空字段的呈现；危险动作的确认体验；不要求记住所有底层字段
脚本 明确参数/文件输入，无交互阻塞，能组合管道和定时任务 稳定的结构化结果、退出状态、标准输出与诊断信息分离；能记录和重跑明确失败项 可重复执行、输入校验、跨平台引号和编码、部分成功不能被当作全部成功
Agent 清晰的命令能力边界、显式目标和动作；通常不能等待人工提示 可解析、逐条关联的结果；区分失败、成功、未知、未执行；知道何时停止和请求人工处理 容易因超时或解析失败重复调用；不能把“自动调用命令”理解为“可自主决定任何高风险动作”

脚本和 Agent 需要相同的基础机器接口；Agent 额外需要处理判断不确定性和自动重试风险。三类使用者可以共享业务语义，不必在第一阶段建设三套服务。

原题任务 必须回答的业务问题 直接相关接口 本轮边界
任务一：第一阶段 CLI 产品方案与评审交付物 为谁提供哪些能力、如何使用、为什么能在资源内完成 由第一阶段范围决定 本文件提供分析和候选范围，暂不选方案、不写正式技术设计

3. 接口梳理

3.1 全局合同与返回对象

认证：全部操作需要请求头 X-Admin-Token；管理员令牌不区分角色或操作权限。文档没有登录、发放令牌、令牌有效期等接口。

错误：统一错误体为 {"code": int, "message": string}，错误码表未整理。各操作 responses 只正式列出 200；部分 400 行为写在描述中，未配套完整错误 schema、错误码或失败示例。不能据此假定所有异常都返回 400，也不能假定 HTTP 200 总代表全部条目成功。

类型记法：List<T> 表示 {"items": [T], "total": integer}；T[] 表示直接返回数组；Ack 表示 {"result": string}，示例值为 "ok"，schema 没有将其约束为固定枚举。

对象 返回字段
ContentSummary content_id, title, creator_id, review_status, quality_status, visibility, tags:string[], created_at
ContentDetail 上述摘要字段，加 body, source(app/web/api_import), channels:string[], category_id
ReviewLog action(approve/reject/limit/restore_quality/take_down/restore), operator_id, reason, created_at；不仅包含审核通过/驳回
TagItem tag, group(题材/风格/运营), usage_count, status(active/deprecated)
CategoryItem category_id, name, channels_allowed:string[]
CreatorSummary creator_id, nickname, level(L1–L5), whitelist:boolean, violation_count
CreatorDetail 上述创作者摘要，加 content_total, content_pending, joined_at
ReportItem report_id, content_id, reporter_id, reason_type(copyright/nsfw/spam/abuse/other), description, status(open/resolved), created_at；另定义 resolved_at, resolver_id, resolve_result(valid/invalid)
PromoSlot slot_id, position(home_banner/home_feed_top/category_top), content_id, start_time, end_time, operator_id
OperationLog log_id, action_type:string, target_id, operator_id, detail:string, created_at
ExportJob job_id, status(queued/running/done/failed), download_url, expires_at；完成时才声明提供下载地址
ReviewDailyStat date, operator_id, approved, rejected, avg_seconds

注意：这些响应对象普遍未列 required 字段。字段存在于 schema 不等于每次都保证非空、保证返回；尤其不能自行给失败导出任务补出一个已有的 failure_reason 字段。日期时间参数的格式是 date-time，样例均以 Z 表示 UTC；日报及推荐位的日期筛选是 date，边界和业务时区未说明。

3.2 重点：查询、审核与标签闭环（6 个操作）

3.2.1 GET /admin/contents：筛选内容列表

  • 查询参数均非必填：content_id, creator_id, keyword, tag, review_status, quality_status, visibility, created_from, created_to, page。
  • keyword 匹配标题与正文；三个状态字段枚举见 2.1；时间参数是 date-time；page 是整数，默认 1。
  • 多个筛选条件为 AND；tag 是单个字符串，未声明多标签 OR/AND、ID 数组或任意条件表达式。
  • 返回 List<ContentSummary>。摘要不含正文、渠道和栏目。
  • 每页固定 20 条，没有 page_size。没有声明排序、游标、快照、总数稳定性和越界页行为。
  • 任务二的入口筛选是 review_status=pending。示例中的 total=137 是接口响应示例，不是 mock 数据统计；mock 实际待审核 132 条。

3.2.2 GET /admin/contents/{content_id}：读取内容详情

  • 必填路径参数：content_id:string。
  • 返回 ContentDetail，提供正文、当前完整标签和三个状态，是人工判断及覆盖标签前的重要依据。
  • 未声明版本号、updated_at、ETag、并发条件或不存在对象的具体错误码。
  • 任务二不能只看列表标题就视为完成了内容核查；空正文场景见第 5 节。

3.2.3 GET /admin/contents/{content_id}/review-logs：读取历史记录

  • 必填路径参数：content_id:string。
  • 返回 ReviewLog[]；文档声明按时间倒序返回全部记录，无分页。
  • 动作还包含质量与上下架处置，不能将每条日志都计为一次通过/驳回审核。
  • 材料冲突：该接口的响应示例先列 7 月 10 日、再列 7 月 11 日，与“倒序”相反；mock 的所有 46 组多条日志也为升序。分析真实接口时保留文档声明，制作 mock 响应和判定“最新记录”时须明确处理该冲突。

3.2.4 POST /admin/content-reviews：提交审核

  • 必填 JSON 请求体：items:array；每项必填 content_id:string, action:approve|reject，可选 reason:string。
  • reject 的原因仅为建议填写，服务端合同没有强制；schema 没有 minItems，也没有同一请求内重复 ID 的约束。
  • 单次最多 20 项，超出返回 400。
  • 返回 {"success_count": integer, "failed_count": integer}，没有逐条 ID、结果或失败原因。
  • 重复提交同一 content_id 会追加审核记录。即使审核状态看起来相同，也不能认为调用没有新增副作用。
  • 单条任务可用只含一项的 items 提交，但仍须检查计数，而不是只看 HTTP 200。请求成功返回和超时无响应是不同情况。
  • 未声明允许审核哪些初始状态、是否批内原子执行、处理顺序、是否校验当前仍为待审核。

3.2.5 GET /admin/tags：读取标签库

  • 无参数，直接返回全部 TagItem[]，无分页。
  • deprecated 标签仍可能存在于存量内容。
  • 任务二可据此查明标签是否存在和是否废弃；这只是提供判断依据，当前更新接口并不强制检查。

3.2.6 PUT /admin/contents/{content_id}/tags：替换内容标签

  • 必填路径参数 content_id；必填 JSON 字段 tags:string[]。
  • 返回 Ack，不回传写入后的完整内容或版本。
  • 全量覆盖，不是追加。例如当前 ["恋爱","校园","武侠"]，只发送 ["轻松"]，其语义是替换为这个数组，不能当成新增一个标签。
  • 不校验标签是否存在于标签库；没有声明禁止废弃标签、重复字符串、空字符串或限制标签数量。schema 没有 minItems，空数组在实际业务中的清空规则仍应确认。
  • 如将来提供“新增/移除”命令，那是 CLI 读取旧值后计算新数组的设计；不是服务端已有增量接口，也不自动解决并发覆盖。

4. 哪些现有接口不适合直接暴露给 CLI / Agent

本节先说明附件中的具体行为，再给出影响和可讨论的措施。措施均为设计建议，不是当前能力承诺。

4.1 批量操作：容量与可恢复性是两个问题

现有行为：内容列表固定 20 条/页；审核每次最多 20 项；审核结果只有两个计数；标签按单条内容覆盖。

对 100 条的影响：

  • 在结果充足且分页读取期间不发生变化的前提下，获取 100 条摘要至少 5 页；读完 mock 全部 132 条待审核内容需要 7 页。
  • 100 条审核至少 5 次请求；若 100 条都更新标签，则还需要 100 次标签 PUT。详情读取、状态核对等请求另计。不是“一条用户命令就等于一次 API 请求”。
  • 某个 20 条批次返回 success_count=18, failed_count=2，只能知道计数，无法知道哪两条失败；不能输出声称精确的逐项失败名单。
  • 查询 pending 第 1 页后立刻审核这 20 条，再查第 2 页，筛选结果可能缩小，导致跳过内容；排序未声明时还存在重排风险。

可讨论的措施：先收集并去重目标 ID，再开始写入，保留明确输入与结果；可在“20 条一批的较低请求量”和“每次只审核 1 条的较明确结果关联”之间选择。后者处理 100 条要 100 次审核请求，也仍有超时歧义。固定本地 ID 清单能减少目标漂移，但不等于服务端一致性快照。并发数、速率、超时和总执行时限也需明确，现有文档未给出可用阈值。

4.2 幂等性：相同最终状态不等于没有重复副作用

具体行为 直接包装的风险 可讨论的边界
重复审核同一内容会追加记录 Agent 超时后重试可能形成两次审核记录；整批重放会重复处理已成功项 对不确定结果禁止盲目重试；本地操作标识、执行记录可辅助恢复，但合同没有服务端幂等键，不能承诺“恰好一次”
标签为固定数组覆盖 同样数组在无并发时可得到相同标签状态，但接口未保证重复写无日志等副作用；重放旧数组还可能覆盖别人后续修改 区分“状态重复设置”与完整操作幂等；不要仅凭 PUT 方法推断所有副作用幂等
同名标签重复创建返回 400 “确保标签存在”脚本重跑会失败 可以读后判断或解释同名冲突，但读后创建仍有竞态，且同名归一化规则未知
通知即时送达、无频率限制 重试可能重复打扰创作者；100 条任务可能集中发送大量通知 若纳入范围，应单独决定发送意图、去重和限速；现有合同没有幂等或撤回保证
推荐位冲突返回 400 第二次占用可能失败；单看冲突不能证明第一次由本次任务成功创建 查询现有占用用于核查，不把 400 一律当作“已成功”；没有已声明的取消接口

最困难的情形是“服务端已经写入，客户端在收到响应前超时”。本地未记录成功不代表服务端未执行；读到目标状态也不能证明就是本次调用造成的。读日志可以提供线索，但没有请求关联字段且 API 操作人相同，仍不能消除所有歧义。

4.3 数据一致性与并发修改

  1. 审核和标签是两次独立调用。任何执行顺序都可能部分完成：审核成功、标签失败，或标签成功、审核失败。附件没有组合接口、跨调用事务或回滚接口。再提交一次相反审核不是事务回滚，还会追加记录。未来命令需要明确每一步的结果，不能只报一个“完成”。
  2. 标签覆盖会丢失并发变更。例如读取 [科幻, 悬疑] 后准备新增“深海”，期间网页新增“编辑精选”，CLI 再覆盖旧数组加“深海”就会丢掉“编辑精选”。详情和写接口未声明版本条件。写前再读、写后核对可降低和发现部分风险，无法封住读写间隙。
  3. 列表筛选不是写入前置条件。查到待审核后，别人可能已经审核；审核请求没有 expected_review_status 等条件。CLI 本地检查不能成为服务端原子保护。
  4. 分发、推荐位、质量和可见性属于不同动作。文档未声明自动联动或完整状态机，不能为“通过”“恢复”“下架”自动附加其他写入。栏目可用渠道应按目标栏目检查，不能用全部栏目渠道的并集替代。
  5. 举报回销与内容处置分离。先回销再下架可能下架失败；先下架再回销也可能回销失败。不能把 result=valid 解释成“内容已处置”。

4.4 错误处理与输出合同

现有问题：错误码表未整理；200 的审核响应可以包含失败；分发只能知道整单失败而没有标准化逐渠道错误；标签创建成功没有定义响应体；导出 failed 没有错误原因字段。

影响：调用方难以可靠决定是否重试、是否修正输入、是否停止。仅从中文 message 猜错误类别不稳定；把缺失的响应字段补成“成功”会掩盖问题。

可讨论的措施：未来 CLI 定义稳定的机器输出与退出状态，保留必要的 HTTP 状态、原始业务 code 和 message；将本地参数错误、明确的服务端失败、部分成功、网络/解析导致的结果未知分开表达。success / failed / unknown / not_executed 等类别是候选输出语义，不是当前 API 已有枚举。自动重试必须逐类讨论，不能把所有非 200 或超时一律重放；错误结果也不应混入正常数据输出。

4.5 权限与高影响动作

现有行为：一个管理员令牌可调用所有接口，不区分角色权限。下架无需二次确认；白名单影响快速审核和部分风控豁免；推荐位影响线上曝光；通知即时送达。

影响：把原始接口全量交给 Agent，会把普通查询、审核和改变风控/曝光的权限同时开放。CLI 的菜单隐藏或确认提示只是产品保护，不是服务端授权边界；持有同一令牌的调用者仍能直接调用其他 API。

可讨论的措施：第一阶段按明确业务目标只暴露必要动作，预先验证参数和目标，明确人机调用的确认方式与批次规模；凭据从受控配置读取，输出和记录中脱敏。若要求真正隔离不同人的权限、限制 Agent 的服务端权限，则需要上游或受控访问层配合，不能描述成当前令牌机制已经支持。无需为本次分析引入完整权限平台。

4.6 审计与责任归属

现有行为：操作日志描述覆盖全部写操作，但 API 直连统一记录 op_api；日志查询的 action_type 枚举只列出六类，没有举报回销、通知、推荐位、导出、标签创建的独立分类说明。日志 detail 为字符串，没有声明结构化前后值、客户端任务 ID 或请求 ID。当前也没有写入自定义审计字段的接口。

影响：能看到后台发生过操作，不等于能区分哪位运营、哪个脚本或哪个 Agent 发起；客户端自报 operator_id 不会改变服务端已声明的记录规则。无法仅凭 op_api + target_id + 时间 稳定关联一次重试或跨接口任务。日志覆盖声明应保留，但上述操作如何分类、如何查询仍需确认，不能直接说这些操作完全不记日志。

可讨论的措施：客户端保留调用来源、目标、计划变更、各步结果及时间，作为执行证据；这不是可信的服务端身份审计。可按目标和时间查询现有操作日志辅助核对。若要求不可抵赖的操作者身份、完整前后值和可靠任务关联，应列为上游合同缺口。

4.7 其他不能静默忽略的行为

  • GET /admin/tags 能读到废弃标签，而更新接口不校验标签库。若 CLI 增加“只准使用有效标签”的规则，会比上游更严格，还可能阻止原样保存带废弃标签的存量内容，需明确新增与保留存量的不同策略。
  • 通知的条件必填规则只写在描述里，schema 不完整；不能只靠自动生成参数模型就认为校验完备。
  • 审核记录没有分页，积累后可能变大；列表读取存在多页成本，不能默认所有列表都一次返回全部。
  • 异步导出需要定义等待、超时及链接过期后的行为；创建任务成功不等于文件已经可下载。
  • 审核日报是 T+1，不能用于证明刚刚审核成功，也不能仅凭现有样例推算 avg_seconds。
  • 正文、标题和举报描述是业务数据。若未来交给 Agent 判断，应把它们当作待分析内容；本次样例检查未发现需要当作指令执行的业务文本。

标题不唯一、存在较长 Unicode 文本 30 组重复标题，每组 2 条，如 ct_000019 与 ct_000201 同名；ct_000042 标题含 emoji，共 61 个 Unicode 码点 写入必须按 ID 定位；适合验证中文/emoji、表格截断和结构化输出完整保留文本；不是非法标题
推荐位与限流并存、时间端点语义不明 ps_0065→ct_000247、ps_0066→ct_000199 为 limited；按严格区间重叠判断，6 条间无重叠，但 ps_0061/0062、ps_0064/0065 首尾相接 不自行宣布限流内容不能占位。相邻时段是否冲突取决于端点规则，不能用本地半开区间假设替代真实合同

内容时间范围为 2024-12-19T03:14:07Z 至 2026-07-16T22:01:27Z；除 ct_000030 外，其余均在 2026 年 5–7 月。推荐位占用都在 2026 年 7 月。演示应使用附件对应的明确日期条件；以本次分析日期 2026-10-31 查询“最近 7 天”或当前占位，会得到空结果，不能当作功能故障。

5.5 能支持的演示与验证

场景 样例支持程度与注意事项
查询、筛选、分页和详情 300 条内容足够验证多页、AND 条件、单条定位；mock 需要实现接口约定的筛选/投影，不能直接把整个详情数组当列表响应
单条审核与标签闭环 可选 ct_000004：pending/normal/online，正文非空，cat_03 + search_only 合法，标签为恋爱、校园、武侠，无审核日志组和举报。它是候选演示对象，并未执行审核
演示标签变更与核对 如人工指定演示决定为“通过并新增轻松”，完整目标数组应为 [恋爱, 校园, 武侠, 轻松]；这些标签均 active。这只是待选演示决定，不是根据样例自动推导的审核结论或既定规则
100 条目标的选取与执行演示 132 条 pending 在数量上足够；选取时仍须处理 17 条空正文、6 条 limited 等上下文，不等于 132 条都可以自动通过。是否实现批量执行见候选范围
异常提示与稳健读取 可用空正文、长标题、废弃标签、渠道不合法、日志排序和时间冲突验证输出与边界处理；不能让脏数据导致整份列表无法阅读
原始数据重置后重复演示 原始附件可作为初始状态；若后续演示写入，应在副本上建立可重置状态。静态 JSON 本身不会执行审核、追加日志或持久化标签

5.6 不能仅凭现有数据验证的能力

  • 没有 operation_logs、messages、export_jobs 或日报记录。不能把 review_logs 冒充全部操作日志；其中没有标签变更记录。
  • 没有服务端行为实现，不能从 JSON 证明重复审核会追加日志、超 20 返回 400、通知送达或推荐位冲突校验已经运行；这些行为来自接口文档，后续 mock 需显式模拟。
  • 没有批量逐项失败、鉴权失败、超时后已执行、并发改写、进程中断等故障样本。要验证恢复边界，需要另设可控场景，并明确它们是新增验证数据。
  • 没有 nsfw 举报、恢复质量/恢复上架日志，也没有未知标签样本；要覆盖这些分支需补充场景。缺少样本不表示接口不支持相应枚举。
  • 日报 avg_seconds、全量标签使用量等无法可靠地从这份快照计算；可以另造明确标记的演示返回，不应伪装成附件真实统计。

6. 需求边界

6.1 题目明确要求的内容

明确要求 应如何理解
将部分后台能力 CLI 化，服务运营人员、脚本和 Agent 范围是部分能力，没有“所有接口都要包装”的要求
自行决定第一阶段能力和最终使用方式 最终方案应有取舍和可理解的使用流程；本轮保留多个范围供后续讨论
形成可供产品与研发评审的交付物 后续要能评审业务范围、使用方式和风险；本轮分析不是最终产品方案或正式技术设计
资源为 1 名后端，第一阶段计划 2 周 要把异常处理、验证、文档计入成本，不能只按端点数量估算
设计后查询一批待审核内容，选择一条完成审核和标签更新，并写操作说明 必须覆盖两个写动作和结果核查；纯只读方案不能独立满足任务二
说明 Agent 自动调用、可能一次处理 100 条时方案如何变化 不能只写“循环调用”；要解释输入、逐项结果、重复调用、部分失败、恢复、权限与审计边界
使用所给接口和样例作为依据 文档描述是当前行为；允许以本地假数据源演示，不要求真实联网

题面没有明确指定语言、CLI 框架、必须新增后端服务、必须重构现有 API，也没有要求提交可运行程序。“Java 开发实习生”提供岗位背景，不应自动推导出具体框架。本轮用户又明确要求不写代码、不选框架，因此这些工作不在当前交付范围内。

6.2 可以自行设计，但需要明确标注为新设计的内容

  • 第一阶段模块和命令边界、名称与参数、单条动作如何组合、标签采用替换还是提供新增/移除的便利语义。
  • 运营人员的可读输出、脚本/Agent 的结构化输出、退出状态、诊断信息、非交互输入和帮助文档。
  • 参数前置校验、是否要求驳回理由、废弃标签的保留/新增策略、批内重复 ID 的处理、空数组和清空动作的交互。
  • 是否有变更预览、人工确认、明确执行标志、文件输入、批次上限、局部重试与客户端执行记录。
  • 第一阶段是完成单条闭环并说明批量演进，还是直接提供 100 条执行；题面第三项要求说明变化，不应自动扩大为完整批处理平台。
  • 本地演示的状态副本、重置方法和故障场景，以及最终评审材料的组织方式。

这些设计不能改写上游语义。尤其不能自行宣称原接口已有增量标签、逐条审核结果、角色权限、真实操作者透传、幂等键、版本锁或跨接口事务。

6.3 材料无法确定的内容

待确认问题 为什么影响范围或评审 在答案明确前的分析边界
第一阶段是否真的需要可运行 CLI、运行平台和打包要求是什么 题面偏方案评审；实际编码交付和 Windows/Linux 分发会占用额外时间 本轮只分析，候选成本明确按“若实施”估算，不提前确定框架
是否允许修改上游 API，谁能提供联调环境 决定是否有条件补逐项结果、幂等、版本与身份能力 暂按现有 API 合同评估，不将上游改造计入两周的必达承诺
审核业务标准、可审核初始状态、冲突处理和各状态联动 决定哪些内容能由人或 Agent 判断并写入 自动调用不等于自动审核判断；没有标准就不默认自动通过或自动纠正数据
Agent 是提交人工给定决定，还是自行生成审核结论 后者涉及判断质量、责任及额外审核机制，显著扩大任务 两种情况应分别讨论；不把模型审核能力纳入原题默认范围
查询排序、分页变化、时间区间端点、业务时区、关键词匹配细节 决定目标选取是否完整可重复、日期筛选是否准确 不承诺服务端快照、稳定分页或特定模糊匹配规则
审核部分失败的具体原因与处理顺序，空批次/重复 ID 如何处理 决定批次结果解释和重试行为 文档只保证上限、计数和重复提交追加记录，其他须保守处理
写后读取是否立即一致，标签/状态的重复写副作用和并发校验 决定能否用回读作为即时验证或重试依据 回读只作核查依据，不承诺线性一致或并发安全
驳回、下架、分发是否另有隐含通知；空栏目、空渠道、废弃标签如何约束 影响副作用与本地校验策略 只采信明确写出的行为，不自动附加通知/清空/迁移操作
权限制度、令牌发放与保管、审计保留和真实身份要求 影响能否向 Agent 开放写权限，以及能否只用客户端记录 现状是无角色区分与 op_api；强身份审计需要另行能力支持
日志对其余写操作的分类、延迟、结构和查询范围 决定能否可靠验证通知、举报、推荐位等操作 不能将宽泛“全部写操作”描述替代具体可查询合同
请求速率、并发限制、超时、环境容量和错误码含义 决定 100 条的性能、重试和可执行时限 不给出未经验证的吞吐指标，不因为通知无频率限制就推断其他 API 无限流
样例统计口径、时间矛盾、日志顺序与快照冲突的原因 影响验收数据和“正确结果”的定义 保留原始数据，列明冲突，不偷偷清洗成单一解释
导出字段、下载鉴权/续期、统计时区与审核计数规则 影响是否值得把导出与统计放入第一阶段 不是任务二的依赖，不应为补齐未知细节挤占核心闭环资源

这些是需要在最终范围决策前分清的重要未知，不表示现在要逐条中断工作向用户确认。

7. 第一阶段功能范围候选

7.1 比较口径

下面是可供选择的不同重点，不是依次叠加的路线，也不在此确定最终方案。

成本是粗略规划估算，假设 1 人、2 周约 10 个工作日，使用当前合同和本地样例，不等待上游改造。估算包含必要的本地演示、输入校验、失败呈现、验证和操作文档；不是承诺，也不是正式排期。若最终只要求方案与文档，可运行实现对应的成本不应被误认为题面硬性要求。

所有完整候选都需要：覆盖单条审核和标签更新的实际演示路径，写清两个独立动作的结果，并在文档中回答 Agent/100 条的变化。任何方案都不能以“客户端处理过”为由承诺服务端强幂等、跨接口原子性或可信身份审计。

7.2 三种完整候选

候选 第一阶段范围 业务价值 粗略总成本 主要风险与取舍 三项任务的覆盖方式
A：运营单条闭环优先 重点 6 个操作：筛选、详情、历史、单条审核、标签库、标签替换；提供基本可读/结构化结果及两步失败提示。写入以明确单条 ID 为主 最直接验证任务二，便于运营理解真实标签覆盖与状态语义；范围集中 6–8 人日，约留 2–4 日缓冲 第一阶段不提供完整 100 条写入执行；两步部分完成仍需人工处理，超时歧义不能消除 任务一聚焦单条产品体验；任务二完整；任务三以具体行为变化和接口缺口说明完成
B：脚本 / Agent 批量调用优先 同样围绕核心 6 个操作，重点放在明确文件输入、最多 100 个目标、重复 ID 校验、逐内容/逐步骤结果、串行或受限执行、执行记录与未知结果停止；减少交互式体验 能检验真实机器调用、部分失败和恢复，是三项任务中批量问题最直接的落地探索 9–12 人日，两周有超期风险 单项审核可改善结果关联但增加请求；20 项批量降低请求却缺逐项结果。必须选取受限策略；不能承诺自动重试所有未知项，崩溃后的精确去重也无上游保证 单条可作为批量为 1 的路径完成任务二；任务三既有说明，也有受限的批量演示；强保证列为未满足边界
C：单条闭环加只读处置上下文 A 的 6 个操作，加创作者详情、按内容查举报、查操作日志，合计约 9 个操作；不扩充处置类写入 审核前能看作者与举报背景，写入后有更多核查线索，适合产品评审业务完整性 8–10 人日，缓冲较少 更多聚合展示与口径冲突处理；mock 缺操作日志，需明确标记补充样本。op_api 仍无法可靠区分调用者，100 条执行留待后续 任务二有更丰富判断上下文；任务三仍以演进说明为主，不暗示已提供完整批处理恢复能力

三者的核心差别是：A 把资源放在最小闭环和交付确定性；B 把资源放在机器执行的结果与恢复；C 把资源放在运营判断与核查上下文。B 的超期可能来自执行语义，而不只是增加几条命令；C 增加的只读数据也会带来样例口径冲突，不能只按 GET 接口数量估算。

7.3 可作为前置增量、但不能独立交卷的范围

只读查询 + 输出待执行清单：内容列表、详情、历史、标签库，约 3–5 人日。价值是快速验证筛选、分页和人机输出，也便于先观察异常数据；但没有完成审核和标签写入，不能单独满足任务二。只有明确把它作为上述完整方案的中间里程碑时才成立。

7.4 本轮范围比较暂不加入的扩展

全量后台包装、自动内容审核模型、白名单修改、上下架/限流、推荐位占用、自动通知、举报处置联动、异步导出和日报，都不是完成任务二的直接依赖。它们分别增加权限、副作用、跨动作一致性或异步状态处理成本。后续可以基于业务优先级重选，但不应为了“看起来功能齐全”默认加入。

现阶段也没有证据要求引入微服务拆分、消息队列、工作流引擎或完整权限平台。范围决策应先明确要交付的业务闭环与可接受的执行保证，再决定是否需要任何新增组件。

后续评审最值得比较的是：第一阶段主要帮助谁完成什么工作、100 条是否必须在第一阶段真实执行、遇到未知结果可以接受怎样的人工介入，以及是否有条件改变上游合同。以上候选保留选择空间，本文件不选定最终方案。
