## 2. 业务流程与事实边界

1. **查询待审核**：完整保留真实第一页 20 行、初始 132 条；ct_000004 实际位于第二行，按钮可选择并进入详情，返回列表后高亮。

4. **确认执行**：显示实际使用的 --execute --yes；需点击“查看已记录的执行结果”才展开原有 succeeded/0，两步 acknowledged/matched。点击只控制历史视图。
5. **结果核验**：pending→approved、标签 3→4、悬疑新增、历史 0→1、队列 132→131、revision=2，并保留新 JVM 普通查询与差异验证链接。

当前已实现的是 Mock 单条原型。HTTP、remove/set、人工输入 ID 确认和完整筛选仍待补齐；十工作日计划逐行摘自 docs/02 第 9.1 节，没有变更原排期或工作量。Agent 的计划绑定、审批、写前意图、批次账本、执行器/恢复仍仅设计，没有执行 100 条。

任务二新增“悬疑”；S5 每场景使用独立副本，新增“轻松”。代表结果切换不改变主流程快照，也不将各场景历史合并。partial 后只补标签；unknown 不因后续查到目标值改报成功，不自动重审或回滚。

## 4. 实际验证与复验方式

当前未提供 Browser 插件及其技能；已知 MCP Playwright 阻止 file 导航，因此直接复用本机已有 Playwright 和 Chrome，没有安装前端工程或起 HTTP 服务。

实际运行：

```powershell
node --check demo/app.js
node --check demo/data.js
node --check evidence/demo/verify.cjs
node evidence/demo/verify.cjs --playwright-module <本机已有 playwright 包的绝对目录>
```

也可使用标准 Node 模块搜索路径中已安装的 playwright，省略该参数；验证依赖仅用于开发，打开 HTML 不需要 Node/Playwright。执行使用 `channel: chrome`、全新临时上下文、`setOffline(true)`，直接导航本地 file URL。不使用个人浏览器资料。

最终实测见 [browser-results.json](browser-results.json)：2026-10-31 21:20 左右（UTC+8，精确 UTC 时间以 JSON 为准），Chrome **156.0.8078.74**、Playwright **1.64.0-alpha-1790635538000**。脚本真实退出 **0，571 项断言通过**，零控制台警告/错误、零页面异常；页面请求仅四个本地资源。

### 实际问题与修复

- 首次运行在 197 项后遇到 `.inspector` 严格定位冲突：合并后主流程与折叠故障区都有同名组件。测试收紧为各自模块作用域，仍分别检查两者。[原始失败](failure-1793452413758.json)。
- 第二次在 287 项后遇到 stderr 文本比对失败。浏览器解析 HTML 时 CRLF 标准化为 LF；测试仅对预期显示文本做同等换行标准化，源文件和内嵌原文完全不变。[原始失败](failure-1793452443987.json)。
- 一次 PowerShell 内联替换因引号未生效，改用 apply_patch 完成定位修改；没有依赖该次失败命令的输出宣称通过。
- 截图复核发现旧来源集合缺 docs/04，补回完整排期折叠区；新版保留全部 70 个链接。
- 静态检查修复 CSS 新增规则意外落入 reduced-motion 媒体块的问题，并新增 reduced-motion 字号断言。
- 可访问性复核修复 skip-link 的 workspace hash 原会返回默认页的问题；现在保持当前模块并聚焦主内容。
- 截图前清除自动化留下的焦点并回到页首，避免把测试滚动位置/跳转链接高亮当成默认视觉状态。通过修复后的完整脚本重新取图。
