# 后端可靠性专项审查

## 1. 范围与结论

审查日期：2026-11-01（Asia/Shanghai）。起点为 master / `5647ac60d88b22725f1b1171682fdb556a560566`，工作区干净。依据原题、OpenAPI、附件说明、[02 产品合同](02-第一阶段MVP与CLI产品方案.md)、[03 技术方案](03-Java技术架构与实施方案.md)、[06 任务二记录](06-实际操作记录.md)、[07 Agent 方案](07-Agent批量处理方案.md)、README 与 S5 原始证据，重点审查实际 Java 控制流和磁盘副作用。

**结论：当前 CLI 对受控、串行的单条 Mock 操作具备可验证的预览、授权、持久化、分步核对和异常停止机制；它降低重复与覆盖风险，但不提供强幂等、并发条件更新、跨接口事务或断电持久性保证。**

本轮没有发现阻塞当前单条串行 Mock 演示的 P0 缺陷；稳定复现了三个 P1 边界：

1. **F-01 并发重复审核**：两个 JVM 都通过 pending 检查后，均能成功，历史新增两条。
2. **F-02 标签丢失更新**：在最后检查之后插入的标签可被旧目标覆盖，写后 matched 不能证明保留了并发修改；process 同样存在该窗口。
3. **F-03 标签库时点变化**：active 检查依据计划时的库；计划后废弃的标签仍可能提交。

这些风险在 02/03/07 中已有边界说明；本轮将其变为确定性、可复现的文件与 JVM 证据，**不是已修复，也不是生产事故**。若交付条件改为同 ID 并发写入安全、提交时强制 active 或真实后台无人值守执行，应将相应能力视为上线阻断条件，不能继续以“单条原型”名义承诺保证。

本轮只新增测试、测试辅助工具、本报告及独立证据。**生产 Java、pom、命令合同、HTML/Playground、原题/OpenAPI/Mock、docs/01–07、任务二工作副本及 S5/HTML 历史证据均未修改。**完整索引在 [evidence/reliability-review/README.md](../evidence/reliability-review/README.md)。

### 2.1 怎样稳定复现，而不是依赖启动时机

新增的 ReliabilityProbe 只存在于 `src/test`，不在交付 JAR 中。它在真实 Gateway 写方法的**委托前**设置文件屏障，底层仍为打包的 CliRunner、ContentService、JsonMockGateway 和 JsonStateStore；没有替换为“预设 succeeded”。

父测试等待两个子 JVM 都生成 ready 标记，确认已完成两次详情读取且看到 pending，再明确放行 A，等其写入/回读/退出后才放行 B。10ms 轮询只用于等待明确标记，存在总超时；**决定交错的是屏障与释放文件，不是随机 sleep**。stdout、stderr、PID、精确参数数组、真实退出码和磁盘摘要均保存。

这证明了**本地 Mock 的真实跨 JVM 竞态**，并核验复用的 CLI 信封与进程码；没有声称未经包装的 `Main` 自带屏障，更没有声称复现了生产 HTTP 事故。最终以新的未包装 JAR 查询实际状态和历史。普通顺序场景直接使用 java -jar。

## 4. 关键复现与实际数据变化

每个独立场景初始均为 ct_000004=pending，标签恋爱/校园/武侠，历史无该组、revision=0。以下结论取自最终回归的 [场景索引](../evidence/reliability-review/scenarios/index.json)，不是手填的预期输出。

### 4.1 A：正常顺序重复审核

未包装的 JAR 第一次 review approve 执行，退出 0；新 JVM 再次同 ID approve，退出 2、REVIEW_NOT_PENDING；第三个 JVM history 为 1。第一次后与重复调用后的快照字节相同，revision 一直为 1。

结论：**顺序重复保护有效**。它来自先读当前状态，而不是保存了幂等键。更换 invocation_id 不会改变保护机制；Gateway 自身仍按附件约定对重复提交追加记录。

### 4.2 B：两个 JVM 都通过检查后提交审核

| 严格受控顺序 | 实际观察 |
| --- | --- |
| A 与 B 各读详情生成计划、执行前再读；到提交委托前阻塞 | 两个 ready 均 pending、detail_reads_before_write=2，请求 items 各 1；尚无业务快照 |
| 只放行 A，等待 A 完成 | A succeeded/0，approved，历史 1，revision 1 |
| 再放行已通过检查的 B | B 仍获 1/0 并 succeeded/0；最终 approved、历史 2，revision 2 |
| 新 JAR get/history | 确认上述磁盘事实，原三标签未变 |

两份进程输出都与各自实际退出码一致。文件锁使两份完整快照**串行写入**，没有让 B 重新执行 Application 的 pending 检查；Gateway 合同也没有 expected_pending。两条日志不等于文件损坏，而是两个业务请求都被执行了。

**四个概念的区别**：pending 前置保护能拒绝已观察到的旧状态；本地文件锁避免快照写乱；服务端条件更新须在同次业务提交中检查期望状态/版本；幂等键则还需绑定请求内容、保存去重结果并与状态/日志原子提交。四者不能互相代称。

### 4.3 标签计划之后变化：能发现的窗口

A 已形成“原三标签＋悬疑”的 OperationPlan；B 实际提交“原三标签＋轻松”。A 执行时重读发现变化，返回 rejected/2、STATE_CHANGED、tags.not_sent；B 的快照 SHA 与 revision=1 保持。审核旧计划的对应测试也拒绝 A，历史仍 1。

这是**同 JVM 控制两个真实存储调用者的代码级测试**，不是独立 CLI 预览对后续调用的强绑定。CliRunner 每次 execute 仍重新生成计划，跨调用审批绑定未实现。

### 4.4 最后检查与标签 PUT 之间变化：无法发现的窗口

跨 JVM 场景中，A tags update 已完成两次 GET、计算完整目标并到达 PUT 委托前；B 用未包装 JAR 新增“轻松”，退出 0、revision=1。放行 A 后，它用旧数组新增“悬疑”并覆盖全量目标。

实际最终结果：A succeeded/0、tags.acknowledged/matched；标签为 **恋爱、校园、武侠、悬疑**，**B 的轻松丢失**；审核仍 pending、无新增历史，revision=2。原始正文、质量和可见性没有被这个标签命令主动变更。

同一风险在 process 的真实文件测试中也复现：审核提交/核对后 B 先新增轻松，A 再 PUT 自己的旧目标。最终 A succeeded，历史 1、revision=3（审核、B 标签、A 标签三次提交），轻松仍丢失。

写后核对只能确认“现在与 A 的目标相同”，不能知道两次 GET 之间是否存在一个已被覆盖的 C。**当前 CLI 是降低覆盖风险，不能保证不覆盖并发修改。**

### 4.5 标签库在计划后废弃新增项

在独立工作副本中，A 计划时悬疑为 active；测试明确将库中该项改为 deprecated 后，A 执行仍 succeeded，当前内容新增悬疑。库变更和标签写入各一次，revision=2。

这是显式夹具，不是原始样例异常，也不是当前 CLI 具有标签库编辑命令。它说明校验是计划时点策略：execute 只重读内容，不重读标签库；即使新增一次库读取，也仍有提交间隙。03 已声明该限制。若必须保证提交时 active，最终仍需服务端在同次更新中校验。

### 4.6 部分失败、响应丢失与核对失败

源码的正常 process 路径为：CliRunner 校验两项执行参数 → plan 读取详情和标签库、校验全部输入 → 默认返回 preview；授权执行才进入 execute → 再读详情比较 → 单 item 审核 → 检查恰为 1/0 → 回读审核并检查标签仍为原值 → 有变化才 PUT 完整标签 → 回读同时核对审核和标签。对应现有调用顺序断言为 `get, library, get, review, get, put, get`；标签无变化时明确 skipped。没有一个隐藏的联合提交。

本轮不重新设计 S5 注入器。源码确认它在真实 delegate 成功持久化之后才抛 WRITE_UNKNOWN；回读故障仅修改一次返回视图，不回写旧数据。既有 FaultInjectingGatewayTest 与 CliProcessIT 在本轮完整 verify 中重跑，读取了真实 state.json、revision、日志，并由新 JVM 核查。

| 情况 | 原调用结果 | 磁盘事实与停止/恢复 |
| --- | --- | --- |
| 审核成功，标签 delegate 前明确拒绝 | partial/4；review acknowledged/matched，tags failed | approved、历史 1、原三标签、revision 1。仅用独立标签命令重新计划；恢复后历史仍 1 |
| 审核提交后丢响应 | unknown/5；review unknown，tags not_sent | 磁盘已 approved、历史 1、revision 1；审核只尝试一次，不继续标签 |
| 标签提交后丢响应 | unknown/5；审核成功事实保留，tags unknown | 磁盘已有目标标签、revision 2；不重发 PUT，不提升原 unknown |
| 审核已确认但回读异常/旧值 | verification_failed/6 | 保留 acknowledged，停止标签；不可读为 unavailable，旧值为 mismatched |
| 标签已确认但最终回读异常/旧值 | verification_failed/6 | 已提交事实不撤销；同时检查审核与标签，不因目标标签相同就忽略审核改变 |

S5 的故障/独立恢复完整原文继续引用 [原索引](../evidence/s5/README.md)，没有复制改写成“本次生产故障”。读后 unavailable 的额外分支由现有 RecordingGateway 单元测试覆盖，不能说所有分支都已经真实 HTTP 实测。

## 5. 文件存储、失败分类与保证边界

### 5.1 实际运行的存储验证

- 双 JVM 从同一明确 start 屏障开始，各提交 20 个独立合成 marker。各完成前 10 次后停在锁外，父测试/新的 JAR 读取完整中间快照：revision=20、marker=20。继续后为 revision=40、marker=40，所有 40 项值正确，无临时文件残留；去除测试 marker 后完整业务树与 seed 相同。
- 文件锁超时的新增写场景中，另一个句柄始终持锁；2 秒后为 REJECTED_NO_COMMIT/STATE_LOCK_TIMEOUT，mutation 根本未调用，原快照字节不变。原有独立 JVM 读锁超时测试同时通过。
- 原子移动故障在**测试自己的工作目录**中，将已载入的 state.json 保留到备份，再把提交目标阻塞为非空目录。真实 Files.move 抛 AccessDeniedException，store 返回 WRITE_UNKNOWN/STATE_COMMIT_UNKNOWN，未返回成功；临时文件清理，备份字节与旧快照一致，阻塞目标继续读取报错而不回退 seed。目标目录是测试故意造成的，不能说生产写入自己把文件变成了目录。
- 缺 tags、null tags、非数组 tags 的工作副本均不能生成写计划，READ_FAILURE，原无效快照字节不变。存储层的集合形状检查不是全量业务校验，Gateway/DTO 的必要字段校验仍不可省。

### 5.2 不同阶段应如何解释

| 阶段 | 当前实现及判定 |
| --- | --- |
| 参数/授权/前置条件不满足 | rejected/2，尚无写请求；不是上游鉴权拒绝 |
| 计划或执行前读失败 | failed/3；没有可用资料就不生成假预览 |
| 写入口前已知拒绝、取写锁失败、提交前回调/校验/探测失败 | store 的明确未提交为 REJECTED_NO_COMMIT；Application 无先前成功时 3，有已核对审核时 4 |
| 写调用已进入但没有可信响应、计数无法解释 | unknown/5，不能一律当作“失败可重试” |
| 实际移动已尝试并抛 IOException | WRITE_UNKNOWN；本次目标阻塞夹具验证了该路径，不凭异常推断所有文件系统都肯定没提交 |
| 已获成功响应，之后回读不可用/不匹配 | verification_failed/6，保留 acknowledged，不回滚 |
| stdout 丢失、序列化/输出失败、JVM 中断 | 不能取得可信完整结果；不自动重放。正常 JSON 与进程码一致不覆盖这种无法可靠交付输出的情形 |

在写路径中遇到含义不明的其他 RuntimeException，Application 保守保留 unknown，不把它转成确定未提交。部分存储读取错误发生在写入口时也可能保守为 5；这不是“未知被误报确定失败”。本轮没有发现可稳定复现的 unknown→明确未提交错误分类路径。

### 5.3 没有验证、也没有承诺的事情

ATOMIC_MOVE 对已有目标的具体处理依赖文件系统实现；当前实现每次先探测，失败就拒绝，没有非原子覆盖回退。这与 [JDK 21 Files.move 合同](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...)) 一致，但**本轮没有在实际不支持原子移动的文件系统上运行**。

没有模拟断电、磁盘损坏、所有提交后资源释放异常、网络共享盘或恶意外部修改者；没有在 Linux/macOS/Java 17 JVM 运行。force(true) 与完整快照替换的源码存在，不能据此声称目录重命名在断电后必定持久，也不能把当前文件锁当成分布式锁。原子提交测试不证明整个 process 原子完成。

## 6. 已解决、可缓解与上游依赖

### 6.1 当前原型已验证的能力

默认预览零业务写入；显式 execute+yes；单 ID/单 item；pending/reject 理由/新增 active 校验；存量保留与 no_change；完整快照提交及新进程读取；部分成功与未知的分步表达；不自动重试/回滚；损坏状态明确拒绝。这里“已解决”仅指相应原型用例，不包含并发和生产保证。

审核与标签是两次提交，不在同一事务。自动“反向审核”会产生新记录，也可能覆盖别人决定；自动恢复旧标签同样可能覆盖新修改。审核已确认且核对成功、标签明确失败时，只对**当前**标签做独立计划；未知/核对失败先停下人工核查。没有哪个非零写结果允许原样自动重放整个 process。

### 6.2 只能缓解的能力

重读与差异检查只能发现读取时已可见的变化；串行操作约定、协调维护窗口和单机受控调用可降低风险。当前客户端没有强绑定跨调用预览、持久化步骤意图或可信审批身份；进程崩溃时缺结果的调用仍可能已执行。文件锁也约束不了网页、其他机器和不遵循协议的编辑器。

`--execute --yes` 表示调用者明确要求本次执行，不是登录身份、角色权限、业务/法律审批或幂等令牌。op_mock_cli/op_api 和本地 invocation_id 不能形成可靠的服务端因果关联；标签修改还需要另存本次参数、计划与输出证据，而不是拿审核历史代替标签审计。

### 6.3 需要上游配合的根本措施（均未实现）

| 目标 | 上游所需合同 | 客户端不能单独做到的部分 |
| --- | --- | --- |
| 防止并发重复审核 | 在更新状态与追加日志的同次提交内验证 expected pending/版本；配合可查询的 operation_id/幂等记录 | 单独本地先 GET 或给请求加任意 UUID 不能获得去重 |
| 安全重发同意图 | 幂等键绑定目标、调用主体和请求摘要，保留明确期限，原子保存结果并能查单 | invocation_id、重启或本地账本不能证明服务端未执行 |
| 防止丢失标签更新 | 返回版本或强 ETag，服务端原子验证 If-Match/expected_version 后更新；冲突后重新读取/审批 | 多读一次仍有窗口；没有上游支持的 If-Match 头无效 |
| 减少全量覆盖 | 可选服务端原子 add/remove，并定义重复副作用、标签合法性与幂等 | 仅改名 PATCH 不能自动安全 |
| 提交时标签合法 | 同次写入验证标签存在/active，或校验标签库版本 | 计划后再读一次只能缩小间隙 |
| 身份与审计 | 受限服务身份、操作权限、真实调用主体和 request/operation 关联 | 当前统一管理员令牌和 op_api 不能由 CLI 菜单补成 RBAC |

条件更新的协议机制参见 [RFC 9110 If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)。这些是后续建议，没有修改 OpenAPI，也不把 Redis、数据库或消息队列列为本次原型的必需条件。

### 7.1 打包观察及其实际影响

开始时 JAR SHA 为任务二记录的 `16859da000d14e9d6b02fe73a330b3a5eedc647f6862d0b20e3ad5675d5091e2`；本轮最终为 `a42bf7cbb747a75ad7373c4142d70ac62ff39af1bf0cfbd872eb718b4192e2ef`。源码未变，当前 JAR 的 seed SHA 正确且不含测试辅助类。相邻两次归档比较显示：条目集合及所有条目解压内容相同、条目顺序不同；不能由此推导已经逐字比较过最初 16859… 的全部条目，因为原始归档未另存。

Maven 日志显示再次打包有大量依赖类重叠警告；当前 jar 插件未设 forceCreation，Shade 会处理现有产物。后续可评估 jar 插件 forceCreation 与固定 outputTimestamp，再验证连续构建；[官方参数说明](https://maven.apache.org/plugins-archives/maven-jar-plugin-3.4.2/jar-mojo.html) 明确讨论了后处理场景。**本轮没有改 pom，也不把该观察宣称为业务失败或已完成构建修复。**详细证据见 [jar-packaging-observation.json](../evidence/reliability-review/tests/jar-packaging-observation.json)。

最终交付前需要一次候选 JAR、历史证据版本和说明的一致性复核；当前无须为完成受控 Mock 原型强制开启生产业务修复阶段。若要求生产并发或强审批，则必须另安排能力补齐与验收。

## 8. 面试时可以这样说明

> 我把 CLI 的成功定义为“写入获得确认，而且重新读取与目标匹配”，默认只预览，执行需要明确授权。审核和标签分两次提交，所以分别保存结果：审核完成而标签失败只补标签，超时或响应丢失就保留未知，不盲目重试或回滚。pending 检查能挡住顺序重复，但我用两个 JVM 的屏障测试证明了它不是强幂等；文件锁只防快照写乱，也挡不住标签检查后被别人插入的修改。要真正防重复和并发覆盖，需要服务端原子条件更新、幂等记录和结果查询；本地 Mock 验证不能代替这些保证。
